# 变更提案：A 股低频研究桌面工具

> 模块：core；分支：a-stock；状态：用户已授权合并，规格已合并；应用未实现、未验收。

## 变更原因
用户要求基于当前分支设计股票池筛选和日线策略研究工具，必须使用 Rust GUI。已确认首版为 A 股研究、不自动下单，支持 Windows 和 Linux。
当前分支已有日线接入、筛选代码和回测示例，但有效规格仍定义为无 GUI 的引擎／库，需要补齐桌面研究应用设计。

## 变更类型
需求级变更，本次交付完整设计规格，不执行代码实现或部署。后续实现以合并后的规格为依据，另建实现提案，逐批交付业务代码、UT/ST 和 OpenLogos reporter。

## 变更概述
设计本地中文桌面应用，贯通“数据准备 → 股票池 → 策略研究 → 回测比较 → 人工交易计划”。界面使用 Rust 编写；既有 Python 数据适配器和 Rust 引擎的复用边界在架构阶段确定。GUI 框架根据官方资料、双平台打包和图表／表格需求完成选型，不预先锁定未经核验的版本。
研究产物保存数据快照、股票池规则及成员、策略参数、成本与成交假设、引擎版本和结果。支持离线使用已有数据；数据更新与回测在后台执行，界面可查看进度、取消任务和读取失败原因。

## 拟议页面
| 页面 | 首版能力 |
|---|---|
| 数据中心 | 通达信导入、TickFlow 更新、数据覆盖与质量检查、复权口径和快照管理 |
| 股票池 | 市场板块、上市时长、价格、流动性筛选；数据具备时的财务筛选；展示入选／排除原因，保存规则及历史成员 |
| 策略研究 | 均线趋势、横截面动量排序模板；日／周／月调仓，持仓数与权重、成本、基准、样本内外区间；有限参数批量实验 |
| 回测对比 | 净值、回撤、收益风险指标、换手成本、持仓成交；比较多个实验与基准，提示数据与假设差异 |
| 交易计划 | 根据完整日线生成信号和目标权重；手工输入现有持仓，计算参考调整量，导出 CSV；无自动下单 |

## 设计验收条件
1. 五个页面形成完整研究流程，每步明确输入、输出、持久化和失败状态。
2. Windows 和 Linux 都有 Rust GUI 构建、安装和验收方案；后台导入、筛选及回测不阻塞界面，取消与恢复语义明确。
3. 历史选股仅使用当时可见信息，定义历史成员、退市、ST 状态和财务公告时间的来源与缺失处理。现有财务模型只有报告期，不能直接视为历史可见时间；必要数据缺失时阻止相关严格回测或明确限制，不静默使用最新信息。
4. 区分复权研究价格与实际成交价格；定义公司行为、交易日历、停牌、涨跌停、交易单位、可卖限制、税费与滑点的建模边界。具体规则在正式设计时查验官方来源，不将日线 OHLC 当作保证成交的盘口。
5. 明确收盘信号与后续模拟成交时点，保存运行版本，隔离样本内参数搜索与样本外评估；定义指标公式、无成交和基准缺失的处理。
6. 交易计划保留数据截至日期、信号解释、目标持仓及参考假设；人工登记成交不得伪装为自动执行成功。
7. 所有 API 源自场景时序；测试覆盖计算、编排、GUI、导出及失败恢复。后续 reporter 必须依据真实断言写入 `logos/resources/verify/test-results.jsonl`，不能固定写入通过状态。

## 统一入口与对话交互补充提案（2026-09-30，已确认）

### 为什么：从两个页面系统收敛为一个研究项目

用户要求统一两个原型，以黑色玻璃态呈现工程化策略研究，前端以对话为主要交互，多智能体协作留在后台。本次为既有 S11～S20 的设计级续作，复用现有活跃变更，不创建竞争 guard。用户已回复“按照此方案继续”，授权本补充的 delta 与原型产出；不包含合并授权。

现状依据：core-05 通过跨 HTML 链接访问 core-03 的数据、股票池、策略库及人工计划；两页各自维护内存状态，存在重复的开发与计划入口。core-05 的需求页仍展示角色列表、步骤预算和“开始协作”按钮，没有贯穿全流程的主对话。统一入口必须同时统一导航、项目上下文、版本引用和任务状态。

### 是什么：一个入口、一个项目上下文、持续对话与可操作产物

以 `core-05-ai-workspace-prototype.html` 作为唯一主入口，将 core-03 的数据中心、股票池、策略资产与实验比较能力迁入同一应用壳。core-03 原入口保留兼容导向，旧锚点映射到统一工作区；取消两套开发、验证与计划状态。迁移说明明确：旧原型刷新即清空，不能宣称恢复其历史内存会话。

| 区域 | 设计职责 |
|---|---|
| 左侧窄导航 | 项目切换、新建研究、项目产物树；共享数据中心、股票池、策略库与实验记录 |
| 中间对话区 | 用户表达目标、补充条件、解释结果、提出修改；展示任务进度、待确认差异、产物引用与可执行动作 |
| 右侧产物区 | 同项目标签页：需求、设计、开发、调试、回测实验、验证报告、交易计划；支持展开专注模式 |
| 顶部项目栏 | 当前项目、研究阶段、所绑定版本、数据截至时间、任务状态及原型标识 |
| 按需证据抽屉 | 运行日志、输入输出、失败原因、版本来源与后台任务记录；默认收起 |

默认先呈现项目概览与对话建议；打开产物时保留当前会话。对话为主要入口，文档编辑器、代码编辑器、事件表和实验图表保留直接操作能力。1100 宽视口支持产物区展开与返回对话，1440 宽视口支持并列；切换资源视图不丢失当前项目。

前端不要求用户选择角色、编排智能体或配置步骤预算。只呈现“正在分析需求／生成设计／运行检查”等任务状态及必要确认。后台可以多智能体协作，但数值结果必须来自计算任务；对话引用证据，不能自行把未运行项目标成通过。

### 怎么做：工程化产物与状态

| 阶段 | 可维护产物 | 核心交互和阶段条件 |
|---|---|---|
| 需求 | 需求正文、研究假设、数据范围、约束、验收标准 | 对话生成草稿，用户可直接编辑；展示修改差异，确认后保存新版本 |
| 设计 | 设计说明、处理节点、系统处理流程图、场景时序图 | 两张图来自同一结构化策略逻辑；点击节点查看输入输出、条件和代码映射；未同步修改明确提示 |
| 开发 | 策略源码、参数定义、检查记录、不可变代码版本 | 对话提出修改并展示差异，编辑器精修，检查后保存版本；不能将文本检查标成代码执行成功 |
| 调试 | 固定小样本运行、事件轨迹、变量与账户快照 | 单步、暂停、筛选、定位源码或流程节点；问题与修复版本相互引用 |
| 回测实验 | 冻结输入、历史模拟结果、净值、成本、交易明细、比较结果 | 回测是可单独发起的实验；从曲线或异常成交进入相同实验的事件调试 |
| 策略验证 | 正确性、历史表现、样本外、稳健性及数据边界的证据清单 | 验收标准来自已确认需求，每项链接证据；区分未运行、通过、失败、证据不足、过期 |
| 交易计划 | 目标持仓、现有持仓、差额、资金与约束核对、有效期 | 引用已验证策略版本及最新数据和账户快照；先生成草稿，再检查计划，确认后导出人工参考清单 |

设计图描述预期行为，调试事件描述实际运行；两者不混同。需求或逻辑修改后，受影响设计、代码和结论标记待更新；历史实验保留原冻结输入与原结论。旧版本的验证不自动转移到新版本。

项目上下文统一关联需求版本、设计版本、代码版本、参数、数据快照、股票池口径、成交与费用假设、模拟器或引擎版本。实验保存历史输入；交易计划使用新的数据与账户快照，并记录其与原验证输入的差异，不能直接把回测期末持仓当成当前计划。

### 调试、回测、策略验证与计划验证的边界

| 概念 | 回答的问题 | 在本产品中的关系 |
|---|---|---|
| 策略调试 | 信号、仓位或订单为何这样产生？实现是否符合设计？ | 正确性排查工具；可用回测引擎驱动小样本或重放，但不等于完整策略验证 |
| 回测 | 在选定历史数据与成交假设下，策略表现怎样？ | 产生实验数据，是策略验证的证据来源之一；收益较高不自动代表通过 |
| 策略验证 | 这个冻结版本是否满足事先定义的验收标准？ | 综合测试、调试、样本内外回测、稳健性与数据限制；结论附适用范围 |
| 交易计划验证 | 这一次具体调整在当前数据、持仓、现金和约束下是否自洽、可供执行？ | 检查数据时效、可卖数量、交易单位、费用预留及风险约束；不能保证成交或盈利 |

“回测交易计划”需明确对象：按历史日期反复生成计划并模拟执行，属于对整套策略与计划生成规则的回测；核对下一交易日的一份计划，属于计划验证；对未来价格情景做假设试算，属于情景分析。三种结果应分别命名。

术语依据：[NautilusTrader 回测概念](https://nautilustrader.io/docs/nightly/concepts/backtesting/)将回测定义为基于历史数据的交易模拟；[实盘概念](https://nautilustrader.io/docs/nightly/concepts/live/)说明同一策略代码可跨回测与实盘环境使用，但需理解两种环境的差异。以上页面仅作概念参考，不作为本仓库版本的接口契约；本节的验证分层为产品设计建议。

### 黑色玻璃视觉

主背景采用中性近黑 `#08090c`，面板为低透明度深灰玻璃，细边框与顶部微光区分层级；靛蓝与淡紫只用于主操作、选中态和少量图表强调。编辑器和正文采用更实的暗色底保证阅读，不在所有区域叠加强模糊。成功、失败、待处理同时提供文字和图标；保留清晰焦点与减少动态效果的适配。

### 一条完整的原型演示旅程

用户输入研究目标 → 助手生成需求草稿 → 用户编辑并确认 → 同步生成设计说明、流程图与时序图 → 生成代码草稿并保存版本 → 调试定位示例订单拒绝 → 查看修复差异并保存新版本 → 比较两次回测 → 汇总带证据的验证报告 → 录入账户快照 → 生成并核对交易计划 → 导出。任一步失败、取消或输入过期都保留解释和继续入口。
