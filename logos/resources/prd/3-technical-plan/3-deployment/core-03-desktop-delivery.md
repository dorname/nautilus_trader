# 双平台交付目标

## 双平台交付目标

本轮只设计，不执行部署。实现交付目标：Windows 11 x86_64 原生安装包及便携包；Ubuntu 24.04 x86_64 桌面提供 AppImage／目录包。Linux 首版对 Wayland 与 X11 各跑 GUI 用例；其他发行版列为未验证。两个平台同一业务版本、协议和固定测试数据，不以交叉编译成功代替实际启动。

## 构建与运行依赖

在 Windows MSVC 与 Ubuntu 本机 CI 分别构建 Rust GUI／worker；遵循仓库 Rust 1.98.1 与锁文件，依赖锁定后记录构建SHA和工具链。初次实现必须先验证 GUI、引擎与Python桥接可同时打包；失败时修正实现方案，不交付只能运行截图的壳。
Python 桥接使用随包隔离运行时，打包其实际所需的Parquet依赖和适配器，不依赖用户PATH中的Python。运行时、字体和动态库均写入版本／许可证清单；离线启动不得临时下载依赖。中文字体随包，选择允许再分发的字体并携带许可证。图形初始化失败给出中文诊断与日志入口，不能假定服务器无显示环境可通过GUI验收。
图形渲染使用eframe的wgpu路径；实现首批验证目标机驱动。没有可用图形后端时启动失败并提示，不把软件渲染支持当作已验证承诺。

## 数据目录与升级

工作区由用户选择，内含 metadata.sqlite、objects/、staging/、exports/；设置和脱敏日志存放于系统用户应用数据目录，Windows用LOCALAPPDATA，Linux用XDG目录，均不写安装目录。工作区路径支持中文和空格；导入外部目录只读。
升级前退出任务、关闭数据库、备份metadata与manifest，先对备份副本执行迁移并检查引用，再切换；失败恢复旧数据库与旧应用。不支持旧程序打开新schema，不自动降级数据。用户删除软件默认保留工作区；清理数据为独立显式操作。

## 发布与验收门禁

未来实现提案必须包含打包代码、依赖许可证清单、两端GUI证据和真实UT/ST reporter，再请求verify。若安排安装部署，需独立获得用户授权并执行本方案；部署后再获得smoke授权。当前提案不包含部署执行任务，不宣称安装包已经存在。
安装包验收：离线启动→导入固定日线→股票池→小型回测→结果→计划CSV→关闭重开。双平台都检查哈希、中文输入、150%缩放、路径、取消和崩溃恢复。用例在 core-desktop-smoke-test-cases.md，任一平台失败不得标记双平台完成。

## 本地开发启动前置

本提案（astock-desktop-launch）交付本地启动形态，不执行部署、不宣称安装包已存在。构建前置：

- **egui/eframe/egui_plot 依赖获取**：网络可用时 `cargo fetch` 后锁定 Cargo.lock；
  离线环境以 `cargo vendor` 离线化或写入本地缓存。实际获取方式与锁定版本记录于
  实现 manifest。锁定前不进入后续批次。
- **本地启动入口**：批次 L1 后 `cargo run -p nautilus-research-cli -- --workspace <路径> <子命令>`；
  批次 L2 后 `cargo run -p nautilus-research-desktop`。
- **无显示环境（WSL2 无 WSLg／服务器）**：GUI crate 保持可编译，验收以 CLI 链路＋
  headless 单元测试承载；渲染与缩放类用例诚实标注 [manual]／skip，不以软件渲染
  截图冒充双平台 GUI 验收（与上文「不把软件渲染支持当作已验证承诺」一致）。
- **双平台安装包交付与 smoke**：维持上文门禁——独立部署级提案＋用户授权后才执行；
  本提案完成不改变该边界。
